# CommCodeChecker

Настольное приложение для нормализации коммерческих кодов номенклатуры
перед загрузкой в 1С. Обрабатывает значения по набору правил, разделяет
результат на «коды для загрузки в 1С» и «коды для ручной проверки»,
формирует отчёт.

Windows Forms, .NET 8.

## Возможности

- **Одиночная проверка** — ввод артикула и коммерческого кода, разбор по шагам
  с подсветкой того, какие правила сработали.
- **Групповая обработка** — загрузка Excel-файла, обработка всех строк,
  разбиение результата на файл для 1С и файл ручной проверки.
- **Проверка ИМ** — отдельный набор правил для кодов интернет-магазина.
- **Настраиваемый набор правил** — каждое правило включается и выключается
  независимо; часть правил связана друг с другом и включается совместно.
- **Внешние файлы конфигурации** — списки слов, окончаний, исключений
  и карта замен символов лежат в отдельных файлах и правятся без пересборки.
- **Отчёт** — сводка по применённым правилам, количеству строк в каждой
  категории, сбоям и дубликатам кода.

## Сборка и запуск

```bash
# Клонирование
git clone https://github.com/<пользователь>/CommCodeChecker.git
cd CommCodeChecker

# Сборка
dotnet build src/CommCodeChecker/CommCodeChecker.csproj -c Release

# Запуск
dotnet run --project src/CommCodeChecker/CommCodeChecker.csproj
```

Публикация в папку:

```bash
dotnet publish src/CommCodeChecker/CommCodeChecker.csproj -c Release -o ./publish
```

Готовый профиль публикации лежит в
`src/CommCodeChecker/Properties/PublishProfiles/FolderProfile.pubxml`.
Перед использованием поменяйте в нём `PublishDir` на свой путь.

> Файл `FolderProfile.pubxml.user` не хранится в репозитории — он содержит
> абсолютные пути машины разработчика и историю публикаций.

Разделение `Core` и `UI` намеренное: вся логика обработки лежит в `Core`
и не зависит от форм. Это позволяет прогонять `SelfTest` и добавлять
новые проверки, не поднимая интерфейс.

## Файлы конфигурации

Папка `Файлы конфигурации` создаётся автоматически при первом запуске
рядом с исполняемым файлом. Каждый файл можно заменить своим — путь
задаётся в разделе «Настройки → Файлы конфигураций».

| Файл | Формат | Назначение |
|---|---|---|
| `Значащие слова.txt` | текст | слова, которые удаляются из значения |
| `Удаляемые_окончания.txt` | текст | окончания, отбрасываемые в конце значения |
| `Артикулы_исключения.xlsx` | XLSX, 3 листа | артикулы, при которых код не нужен |
| `Слова удаления кода.txt` | текст | слова, при которых код удаляется целиком |
| `Замены символов.xlsx` | XLSX, 2 колонки | карта замен символов |
| `Правила проверки комм. кода для ИМ.xlsx` | XLSX | правила для кодов ИМ |
| `Правила проверки артикула для ИМ.xlsx` | XLSX | правила для артикулов ИМ |
| `правила обработки значений коммерческого кода.txt` | текст | текст справки по правилам |

### Текстовые файлы

Формат одинаковый: две строки заголовка, пустая строка, затем значения —
по одному в строке. Значения читаются **начиная с четвёртой строки**.

```
Удаляемые слова
Правила добавления слов: по одному значению в строке, без пробелов в начале и в конце

конденсатор
болт
винт
```

Файл `Слова удаления кода.txt` работает так: если значение начинается
с такого слова, код удаляется целиком, минуя остальные проверки. Это
нужно для групп изделий, где проще удалить код, чем проверять его вручную.

### Файл исключений

`Артикулы_исключения.xlsx` содержит три листа, каждый со своей логикой
сопоставления:

| Лист | Условие |
|---|---|
| `Начинается с` | артикул начинается с указанного текста |
| `Заканчивается на` | артикул заканчивается на указанный текст |
| `Содержит` | артикул содержит указанный текст |

В шаблонах допустим символ `*` — ровно один любой символ.
Первая строка каждого листа — заголовок, данные читаются со второй строки.

## Правила обработки

Правила применяются в порядке, заданном в `RuleCatalog.ApplyOrder`.
Порядок отличается от нумерации в техническом задании: правило 9
выполняется **первым**, потому что при совпадении обработка прекращается
и остальные правила к строке не применяются.

| Порядок | Правило | Что делает |
|---|---|---|
| 1 | Комм. код удалён по виду артикула | проверка по «Артикулы_исключения.xlsx» |
| 2 | Удаление служебных символов | невидимые символы, ломающие шаблоны |
| 3 | Замена тире на минус | все виды тире → `-`, нормализует границы слов |
| 4 | Удаление лишних пробелов | схлопывание пробелов, обрезка по краям |
| 5 | Замена символов в резьбе | `М12х1.5` → `M12X1,5` |
| 6 | Замена «х» в размерах | `20х20х3` → `20x20x3` |
| 7 | Замена точки на запятую | десятичный разделитель в числах |
| 8 | Удаление значащих слов | слова из «Значащие слова.txt» |
| 9 | Удаление окончания | окончания из «Удаляемые_окончания.txt» |
| 10 | Замена кирилл. А на англ. A | гомоглифы, с защитой марок стали |
| 11 | Оставить код, совпадающий с артикулом | приоритет артикула |
| 12 | Проверка кода после значащего слова | классификация остатка |

Номера в таблице — это порядок **применения**, а не идентификаторы в
`RuleId`. В интерфейсе и в отчёте правила показываются в порядке из
технического задания (`RuleCatalog.DisplayOrder`).

Правила «Удаление значащих слов» и «Удаление окончания» связаны — их
можно включить только вместе (`RuleCatalog.LinkedGroups`).

### Правило 10: марки стали

Замена гомоглифов не трогает марки стали на кириллице. Марка
распознаётся по структуре (`08Х18Н10`, `12Х18Н10Т`, `40ХН2МА`) и
защищается от замены целиком.

Проверка работает не только по целому токену, но и по его частям,
разделённым дефисом, точкой, слэшем или запятой. Это нужно для
составных кодов вида `F21-50-PN25-10Х17Н13М2Т-TYPE-E`, где марка стоит
внутри значения: токены выделяются по пробелам, поэтому без разбора
по частям марка не была бы найдена.

### Правило 5: обозначения резьбы

Кириллическая `М` заменяется на латинскую `M` только в обозначениях
резьбы. Условия:

- слева — начало строки, пробел, дефис или минус;
- справа — цифра;
- для обозначений вида `М0…` дополнительно требуется запятая или точка
  сразу после `М0` (`М0,5`), иначе это артикул (`М004`, `М008`).

Обозначения вида `М12`, `М10x1.5` обрабатываются без дополнительного
условия. Артикулы `М004-25`, `М008-25-1` и составные коды с `М` после
дефиса (`КЭМ-М004-РФ01`) остаются без изменений.

## Как устроена обработка

Каждое значение проходит конвейер правил. Состояние строки хранится
в `TrackedString` — он помнит исходный текст, текущее значение и позиции,
затронутые правками, что позволяет подсветить изменения в интерфейсе.

Результат одного прохода описывается `ProcessResult`:

| Поле | Значение |
|---|---|
| `Result` | итоговое значение |
| `ReadyFor1C` | код пригоден для загрузки в 1С |
| `CatalogReviewWithResult` | отправлен на ручную проверку |
| `CatalogReviewEmpty` | результат пустой, код удалён |
| `DeletedByArticle` | код удалён по виду артикула |
| `ProcessingError` | текст ошибки, если обработка сорвалась |

В групповой обработке строки распределяются по трём категориям:
коды для загрузки в 1С, коды для ручной проверки и неизменённые строки.
Отдельно считаются дубликаты кода — строки с одинаковым коммерческим
кодом при разных артикулах.

## Самопроверка

`Core/SelfTest.cs` содержит 48 проверочных кейсов, покрывающих все
правила. Кейсы выполняются через точку входа меню справки и не требуют
внешних данных — на вход подаются строки, на выходе сверяется ожидаемый
результат.

Кейсы сгруппированы по префиксу артикула:

| Префикс | Что покрывает | Кейсов |
|---|---|---|
| `A` | базовые правила обработки | 29 |
| `S` | марки стали | 6 |
| `H` | замена гомоглифов | 4 |
| `P` | удаление служебных слов | 4 |
| `D` | точки в цепочках и размерах | 4 |
| `SRF` | сквозной кейс на реальном артикуле | 1 |
| | **всего** | **48** |

При добавлении правила допишите кейс в `SelfTest.Cases` — это самый
быстрый способ проверить, что правка не сломала соседние правила.

## Выходные файлы

Групповая обработка формирует:

| Файл | Содержимое |
|---|---|
| `<исходный>_1С.xlsx` | коды для загрузки |
| `<исходный>_проверка.xlsx` | коды для ручной проверки |
| `Применённые правила.txt` | сводка по правилам и категориям |

В файле для 1С столбец с кодом остаётся пустым для строк, которые
удалены или отправлены на ручную проверку. Строки с дубликатами кода
помечаются красной заливкой.

## Участие в разработке

1. Создайте ветку от `main`: `git checkout -b fix/rule-5-thread`.
2. Внесите правку и добавьте кейс в `Core/SelfTest.cs`.
3. Убедитесь, что все кейсы проходят.
4. Оформите коммит и откройте pull request с описанием: что изменилось,
   какой кейс добавлен, какие данные проверялись.

Имена веток: `feat/...`, `fix/...`, `docs/...`.

Сообщения коммитов — в повелительном наклонении, на русском или
английском, но единообразно в пределах репозитория:

```
fix: правило 5 не заменяет М после дефиса

Добавлен кейс A30. Проверено на 9 строках из рабочей выгрузки.
```

### Соглашения по коду

- Проект использует file-scoped namespace и nullable-контекст.
- Логика обработки не должна зависеть от `System.Windows.Forms` —
  такие зависимости ломают `SelfTest`.
- Комментарии пишутся по-русски и объясняют причину, а не действие.
  Пример из `CodeProcessor.cs`:

  ```csharp
  // Кириллическая М заменяется на латинскую M только если это резьба
  // с десятичной дробью: М0,5. Это исключает артикулы вида М004, М008.
  ```

Стиль отступов и переводы строк заданы в `.editorconfig`.
